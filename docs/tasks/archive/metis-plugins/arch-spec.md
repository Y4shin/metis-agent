# arch-spec, metis-plugins

Effort-wide architecture spec, shared by every ticket chain in this effort. Each
section below gives one ticket its landed public surface, the existing
abstractions it built on, what it must not reimplement, the seams the tdd-worker
tested at, and the interface contract its dependents call. Where the landed
surface differs from the plan, the section says so and records the superseded
shape beside it. The spec-reconciler folded each landed ticket's committed
deviation report back into this file, one editing pass per level, and the
doc-gate on this repo's prose applies here too: no em-dashes, plain vocabulary,
the glossary's terms.

## Shared conventions

- Branches: landing branch `task/<ticket-slug>`, working branch
  `ticket/<ticket-slug>` created off it, merged back with `--no-ff` and
  deleted. Chains land in dependency-level order, and levels are strict
  barriers.
- Toolchain: devenv only. Every command runs as `devenv shell -- <command>` on
  the toolchain `devenv.nix` pins: Rust nightly, edition 2024,
  `resolver = "3"`.
- Gates, always and in this order: `cargo fmt --check`,
  `cargo clippy --all-targets -- -D warnings`, `cargo test`. The effort's own
  contract and ABI commands are numbers 3 to 7 of `docs/testing.md`.
- Every crate carries `[lints] workspace = true`. New third-party dependencies
  are added once to `[workspace.dependencies]` in the root `Cargo.toml` with a
  comment that says why, and crates reference them as `.workspace = true`.
- Generated artifacts are never hand-edited. The ABI header
  (`crates/plugin-contract/include/metis_plugin_abi.h`) is regenerated by
  `bash scripts/regenerate-abi-header.sh`, and the check form fails when the
  generated file and its source disagree.
- Names fixed already and not to be changed: crate `plugin-contract`, crate
  `plugin-runtime`, crate `plugin-fixture`, entry symbol
  `metis_plugin_entry_v1`, feature gate `authoring`, table type
  `MetisPluginTableV1`, ABI major 1.
- Prose and comments follow `AGENTS.md`: no em-dashes anywhere. The domain
  terms are `CONTEXT.md`'s, not this file's to define: the Language section now
  carries bundle, manifest, capability, target, host context, disabled plugin,
  sink and ordering ledger, and this spec uses those words.

## The landed baseline

What exists today, and therefore what every ticket below builds on.

- `crates/plugin-contract`: the versioned C ABI. ABI major 1, minor 2.
  `MetisPluginTableV1` carries eight slots, `init_plugin` first and
  `service_complete` last, with the slot constants, thresholds and layout
  assertions in `src/abi/layout.rs`. `METIS_PLUGIN_ENTRY_V1` names the entry
  symbol. `src/payload.rs` writes and reads the UTF-8 JSON envelope.
  `src/authoring/` holds the Rust authoring surface behind the `authoring`
  feature: the `Plugin` trait with its asynchronous fallible `init` and no
  `Default` bound, the export adapter, the call and waker bridge, and the buffer
  ownership helpers. `Initialisation` and `HostContext`, the two named parts of
  the initialisation payload, live there too, so they sit behind that gate.
- `crates/plugin-runtime`: the host side. `Loaded` maps a cdylib and reads the
  table through the version gate, `Host` carries the host table plus the
  recorded callbacks, `Instance` owns one instance and its in-flight set,
  `PluginCall` is the polled future, `registry::{Registry, Entry, RouteError,
  RegistryError}` routes and validates. `Loaded::init_plugin` starts one
  instance's initialisation and returns the public `PluginInit` future, which
  the caller drives. Its error surface is settled: one type
  each for load and dispatch (`CallError`), routing and validation
  (`RouteError`) and registration (`RegistryError`). The
  `bundle::{BundleHeader, VerifiedBundle, BundleError, TrustStore, RootKey,
  KeyId, verify_bundle}` surface verifies a signed bundle out of one file,
  `src/bundle.rs`, reached as `plugin_runtime::bundle`, `bundle::extract` stages
  that archive for one host target into a `StagedBundle`, and the host waker
  accounting is `Host::waker_counts()` plus the new `Host::wakes_after_drop()`.
- `crates/plugin-fixture`: the Rust fixture with its ten capabilities, its
  hand-written C twin (`c/c-plugin.c`), the other-major plugin, and the ABI
  harness (`src/bin/abi-harness.rs`) that hand-drives a real host.
- `docs/plugin-contract.md` is v1 text with this effort's amendments already in
  it: the waker rule, in section 8 and section 11 rule 4; the bundle container,
  chain, profile, key id, revocation and refusal rules, in section 17; the
  archive and extraction rules, in section 17.8; and the asynchronous
  initialisation entry, in section 18 with sections 5, 11, 12, 14 and 15
  rewritten around it. `init_plugin` is the table's first slot and the counters
  entry is gone, so nothing there names `create_instance` any more. No other
  ticket edits that file.
- `docs/testing.md` is the command protocol. Tickets that add a command or close
  a recorded gap edit it in the same commit.

## Cross-ticket interface contracts

The chain of surfaces the effort builds, in dependency order. Each later ticket
consumes exactly the surface its predecessor exported, and nothing else.

```text
verify_bundle(bytes, &TrustStore) -> Result<VerifiedBundle, BundleError>   bundle-verification
staged = extract(verified, target: &str) -> Result<StagedBundle, StageError> bundle-extraction
manifest = Manifest::parse(text) -> Result<Manifest, ManifestError>          manifest-and-library
manifest = Manifest::read(&StagedBundle, common_name) -> Result<Manifest, ..> manifest-and-library
loaded = unsafe { Loaded::open(lib_path, &Manifest) }                       manifest-and-library
init = loaded.init_plugin(&host, body) -> Result<PluginInit, CallError>     abi-initialisation-entry
serving = load_bundle(&host, path, config, ctx, trust) -> Result<Serving, LoadError> async-initialisation
instance.cancel_all(deadline: Instant) -> CancelReport                       call-cancellation
Host::with_sink(sink) + Host::for_instance(name)                             callback-sink
start_plugins(dir, config, trust) -> Result<StartupReport, StartupStop>      startup-policy
serving.release(deadline: Instant).await -> ReleaseReport                     teardown-and-release
sample bundle builder + one end-to-end CI test                                sample-bundle-ci
```

### Required state before the dependency levels: the ABI and the waker

`waker-lifecycle-fix` (bug) and `bundle-verification` (feature) are the two
independent, unblocked tickets. The bug is the leaked owning reference at
`plugin-contract`'s authoring bridge, fixed in the host waker in
`plugin-runtime`; the feature adds the bundle verifier to `plugin-runtime`.
Neither depends on the other, and both must land before the rest of the graph.

The bug's interface contract, because `abi-initialisation-entry` depends on it.
The fix landed in the host: `PluginCall::poll` releases the one owning reference
it hands to the poll as soon as that poll returns, whatever it returned, so a
poll that parks, fails or panics cannot leak it, and
`crates/plugin-contract/src/authoring/call.rs` and `future.rs` are untouched by
this ticket. A clone the plugin takes stays the plugin's to release.

Two pieces of the host's public accounting moved. `Host::waker_counts()` still
returns three numbers, and the first one now counts every owning waker reference
the host handed out, one for each poll it runs and one for each clone the plugin
takes, and no longer just the clones the plugin made. The second counts
releases, and the first two are equal when nothing is outstanding; the third is
the length of the late-wake record. `Host::wakes_after_drop() -> Vec<u64>` is
new: it returns the request ids of the wakes that arrived after their call's
future was dropped, in arrival order, so a late wake names the call it belongs
to. `CallState` carries the request id, which is what makes that record
possible. A dependent reads the first number as references handed out, never as
plugin clones.

`MetisWaker` now carries a host-side token in its `data` field, not a raw
`Arc<CallState>` pointer. The token names an entry in a process-wide live-waker
table, and the first `wake` or `drop` of a token takes the entry out, so a
second use of one consumed clone finds nothing left to release and is refused
rather than acted on, which is what makes a double release impossible. The ABI
is unchanged: the field stays opaque, the layout does not move,
`METIS_ABI_MINOR` stayed 1 until `abi-initialisation-entry` moved it to 2, and
the corrected lifetime claim is in the doc
comment in `crates/plugin-contract/src/abi/mod.rs` and in the regenerated
header.

The record rule is worded in `docs/plugin-contract.md` section 8 and section 11
rule 4 as a counted violation rather than an ordering-ledger entry. The measured
reference counts and the three defect statements are in the hazard findings
file, not to be re-derived.

The fixture now exposes ten capabilities, the two new ones being `tool.deferred`
and `tool.wake_deferred`, and the ABI harness's expected list grew with them.
The double wake is provoked by a `#[cfg(test)]` unit test in
`crates/plugin-runtime/src/lib.rs`, because the authoring surface cannot express
it. `abi-initialisation-entry` inherited one host obligation from this fix,
because the ABI harness did not yet release the waker reference its own poll
hands out; it closed that obligation in the harness, and the record is in the
Level 1 landed state below.

#### `bundle-verification` (feature, l)

The cross-cutting decision this ticket serves is ADR 0005's one signed bundle
as the artifact a plugin ships as (`docs/adr/0005-plugin-host-boundary.md`); this
section records the landed surface and does not restate the decision.

**Exports.** A new `plugin_runtime::bundle` module, landed as one file,
`crates/plugin-runtime/src/bundle.rs`, declared as `pub mod bundle` and reached
as `plugin_runtime::bundle::...`. The crate root does not re-export its items.
Splitting the file into a `bundle/` directory was left to `bundle-extraction`,
which did split it: `crates/plugin-runtime/src/bundle.rs` stays the verifier and
`crates/plugin-runtime/src/bundle/extract.rs` holds the extractor, re-exported
so it is reached as `bundle::extract`.

- `TrustStore`: the trust policy as a plain value the daemon constructs. It
  holds the roots as `RootKey` values, each a recomputed key id with the raw
  32-byte Ed25519 public key, and the revoked keys as `KeyId` values, which is a
  `[u8; 16]`. The constructors and mutators are `TrustStore::empty()`,
  `with_root(public_key)`, `add_root(&mut self, public_key)`,
  `revoke(&mut self, id)`, plus the readers `roots()` and `revoked()`.
  `TrustStore::empty()` is the compiled-in default the daemon starts from. The
  runtime never reads a configuration file and never defines the configuration
  file's shape.
- `KeyId` and `key_id(public_key)`: the 16-byte key id type and the function
  that computes it from the raw public key.
- `BundleHeader`: the parsed fixed-size container header, built only through
  `BundleHeader::parse(bytes)`. Big-endian throughout, fixed width because the
  signature's location depends on it.
- `VerifiedBundle`: a borrowed view of an accepted bundle. Its whole public
  surface is `header()`, `archive()` and `leaf_common_name()`: the parsed chain
  is a private field, so `x509_cert::Certificate` never enters this crate's
  public API, and a later ticket that needs a chain detail adds an accessor
  first. Nothing is copied, and nothing is extracted.
- `BundleError`: 26 variants, one per refusal rule, in this crate's existing
  error style (`CallError` and `RouteError` are the models: a plain enum of
  struct variants, `Display`, `std::error::Error`, no panic path). The variants
  are `Truncated`, `BadMagic`, `UnknownContainerVersion`, `UnknownSigningSuite`,
  `BadHeaderLength`, `ReservedNotZero`, `BytesBeforeHeader`,
  `ChainSpanMismatch`, `SpanMismatch`, `EmptyChain`, `ChainTooLong`,
  `TrailingChainBytes`, `NonCanonicalDer`, `MalformedCertificate`,
  `UnknownRoot`, `RevokedKey`, `Expired`, `NotYetValid`, `CaConstraintMissing`,
  `LeafIsCa`, `UnknownCriticalExtension`, `ChainBroken`,
  `ChainSignatureInvalid`, `MalformedSignature`, `SignatureInvalid` and
  `MissingCommonName`. That is the planned families plus eight variants the plan
  did not name, so the variant set is wider than planned and a dependent must
  not match it exhaustively.
- The constants `CONTAINER_MAGIC` (`METISBND`), `CONTAINER_VERSION` (1),
  `SIGNING_SUITE` (1), `HEADER_LENGTH` (40), `MAX_CHAIN_LINKS` (8),
  `KEY_ID_LENGTH` (16) and `DOMAIN_TAG`.
- `verify_bundle(bytes: &[u8], trust: &TrustStore) -> Result<VerifiedBundle<'_>,
  BundleError>`: the one entry point.

**The container, as this spec fixes it, so a second implementation can be
written from the contract alone.** A 40-byte header, then the chain region, then
the signature, then the ZIP bytes, and the file length equals signature offset
plus signature length plus ZIP length, so no byte escapes the signed range.

| offset | size | field |
| --- | --- | --- |
| 0 | 8 | magic, the ASCII bytes `METISBND` |
| 8 | 2 | container format version, `u16`, must equal this build's exactly, currently 1 |
| 10 | 2 | signing suite, `u16`, currently 1 for X.509 over Ed25519 |
| 12 | 2 | header length, `u16`, must equal 40 |
| 14 | 2 | reserved, `u16`, must be zero |
| 16 | 4 | chain length, `u32` |
| 20 | 8 | signature offset, `u64`, must equal header length plus chain length |
| 28 | 4 | signature length, `u32` |
| 32 | 8 | ZIP length, `u64` |

The **signed message** is the domain tag, then the header bytes, then the chain
bytes, then the ZIP bytes, with the signature bytes themselves deleted rather
than zero-filled. The domain tag is a fixed byte string independent of the
container version, so a container version bump does not change it; its bytes are
the 27 ASCII characters `METIS-PLUGIN-BUNDLE-PAYLOAD`, exported as `DOMAIN_TAG`,
so a producer signs `DOMAIN_TAG || header || chain || archive`. The signature is
raw Ed25519 over that message, verified with `verify_strict`, so a non-canonical
key or signature encoding is refused.

**The anchor, the profile and the validity window, fixed here**, because a
producer and a dependent both have to match them. The chain carries the anchor's
own certificate as its last link, and the anchor is trusted by the key id
recomputed from its public key rather than by who signed it, so a chain that
omits the anchor's certificate is refused as an unknown root. `basicConstraints`
is the only extension this build understands: any other critical extension
refuses the chain, and every other non-critical extension is ignored, so a
producer may carry its own key identifier and this build will not trust it. A
certificate that authorises another key carries `CA:TRUE`, the leaf-authorising
certificate is an end entity, and a link's validity window is checked at second
granularity against the host's clock with 60 seconds of skew tolerated at each
end.

**Crates chosen here, with their cost measured and recorded.** The token
`ed25519-dalek` 3 over `curve25519-dalek` 5 for verification, `x509-cert` 0.3
over `der` 0.8 (`spki` 0.8, `const-oid` 0.10) for strict DER and the certificate
profile, and `sha2` 0.11 for the key id. All are pure Rust, and no C compiler is
in the path that reads untrusted bytes. The measured count at `plugin-runtime`
is 66 crates before this ticket and 85 after for normal edges, so the trusted
parse path adds 19 including its four direct crates, and 76 before and 101 after
when the test-only signer's dev-dependencies are counted. The only added crate
with a build script is `curve25519-dalek`, whose script selects cfg flags from
the rustc version and compiles nothing. The signer's extra features
(`x509-cert`'s `builder`, `ed25519-dalek`'s `alloc` and `pkcs8`) are
dev-dependencies only, so no shipped build compiles a signing path. The counting
pipeline is `cargo tree -p plugin-runtime --edges normal --prefix none | grep -v
'(*)' | sort -u | wc -l`, with the `grep` filter because `cargo tree` prints a
repeated subtree as a marker line that survives `sort -u`. The counts are
repeated in the ticket's implementation note and in the contract's dependency
paragraph, and contract 17.7 lacks that filter, which is one of the carried
risks below.

**Key id rule, fixed here.** The key id of a public key is the first 16 bytes of
its SHA-256, computed over the raw 32-byte Ed25519 public key, never over the
SPKI wrapper. A carried identifier is never trusted. Revocation entries name
keys by that id.

**Refusal classification, fixed here** because `startup-policy` consumes it:
`BundleError::is_trust_failure()` answers true for the outcomes that mean
"this file claims a signature we do not trust": a missing or malformed
signature, a signature that does not verify, an empty chain, an unknown root, a
revoked key, an expired or not-yet-valid certificate, and every chain profile
violation. Those stop daemon start-up. The container-format outcomes (bad
magic, unknown container version, a span that does not account for the whole
file, bytes before the header, a non-canonical DER encoding, trailing bytes in
the chain region, more than eight links, a malformed certificate, a non-zero
reserved field) degrade that one bundle instead, because there is no evidence of
tampering, only a file this build cannot read. Bytes before the header, as the
landed check reads it, is a declared signature offset below the header's end,
checked before the rule that the offset equals the header length plus the chain
length, because one header can trip both. `startup-policy` calls
`is_trust_failure()` as a predicate rather than matching `BundleError` variants,
because the landed variant set is wider than the plan named.

**Existing abstractions to use.** `CallError`'s shape for the new error enum;
`Loaded`'s doc-comment style for the unsafe-free parse path; the workspace
dependency table; the integration-test support module in
`crates/plugin-runtime/tests/support/` for building real artifacts on disk.

**Do not reimplement.** No hand-rolled DER or ASN.1 parser: `der` and
`x509-cert` own the decoding, and the strict decoder is what refuses
non-canonical input. No hand-rolled Ed25519, no `ring`, `openssl`, `aws-lc` or
any other crate that needs a C toolchain. Do not add `rustls-webpki`: its trust
anchor model and its name constraints are not this project's profile. No ZIP
reading in this ticket, since the verifier only has to cover the bytes. No
reading of daemon configuration. No change to the ABI types.

**Seams, for user approval.** One product seam: the public
`verify_bundle(bytes, &TrustStore)` entry, tested from
`crates/plugin-runtime/tests/bundle_verification.rs` with real bytes. One data
fixture: committed bundle vectors with altered copies under
`crates/plugin-runtime/tests/vectors/`. One test-only helper: a signer in
`tests/support/` that issues a small chain and signs a payload with a fixed
test seed, used to build the vectors and to install the test key as a root
explicitly. It landed as `crates/plugin-runtime/tests/support/signer.rs` and is
a deliberate second implementation of the layout: it restates the offsets, the
magic, the container version and the domain tag instead of calling the
verifier's constants, and the committed vectors are rebuilt from it and compared
byte for byte on every run, so a changed byte fails the suite. The daemon's
compiled-in root set stays empty, so no shipped build trusts the test key.

**Interface contract.** `VerifiedBundle::archive()` returns the ZIP bytes,
`VerifiedBundle::leaf_common_name()` returns the name the manifest check
compares against, `VerifiedBundle::header()` returns the parsed header, and
`BundleError::is_trust_failure()` classifies the outcome. The parsed chain stays
private, so a dependent that needs a chain detail adds an accessor first.
`bundle-extraction` consumes `archive()`, `manifest-and-library` consumes
`leaf_common_name()`, and `startup-policy` calls
`BundleError::is_trust_failure()` rather than matching variants, because the
variant set is wider than the plan named and the predicate is the stable seam. A
producer, which is the packaging step of `sample-bundle-ci`, signs the domain
tag, the header, the chain and the archive together and writes the root's
certificate as the chain's last link.

**Doc edits.** `docs/plugin-contract.md` gains a section for the container
header, the chain profile, the domain tag, the key id rule, the revocation rule
and the refusal rules, and the dependency paragraph records the measured count.
`docs/testing.md` gains the vector test if it runs as its own command.

### `bundle-extraction` (feature, m)

**Exports.**
`plugin_runtime::bundle::extract(verified: &VerifiedBundle<'_>, target: &str) ->
Result<StagedBundle, StageError>`, landed as
`crates/plugin-runtime/src/bundle/extract.rs`, declared as a private
`mod extract` in `crates/plugin-runtime/src/bundle.rs` and re-exported, so the
function is reached as `bundle::extract` next to the verifier and the split is
the `bundle/` directory the plan left to this ticket. `StagedBundle` owns a
staging directory and removes it when dropped, so a refused extraction and a
finished load both leave nothing behind. It exposes `root()`, `manifest_path()`
and `library_path()`, and implements `Drop`. The module also exports
`STAGING_PREFIX` and the three limit constants, and its error is `StageError`
with 15 variants: `ArchiveUnreadable`, `TooManyEntries`, `EntryTooLarge`,
`ArchiveTooLarge`, `AbsoluteEntryName`, `ParentEntryName`, `UnusableEntryName`,
`EntryIsSymlink`, `EntryIsDirectory`, `EntryIsNotRegularFile`,
`EntryModeRefused`, `EntryUnreadable`, `MissingTargetLibrary`,
`AmbiguousTargetLibrary` and `Io`.

**Limits.** The landed numbers are `MAX_ENTRIES` 256, `MAX_ENTRY_SIZE` 64 MiB
and `MAX_UNCOMPRESSED_SIZE` 256 MiB, four times the numbers the approved plan
proposed (64, 32 MiB and 64 MiB). They are what contract 17.8 records and what a
producer has to respect, so the approved figures are superseded:
`sample-bundle-ci` and the SDK signing CLI adopt 256, 64 MiB and 256 MiB. The
three constants are imported from `plugin_runtime::bundle`. The per-entry limit
is checked first and the archive total answers for an archive whose entries are
each inside their own limit, and the limits are enforced on declared entry sizes
rather than on decompressed output, so a target this host does not load is never
decompressed. No dependent broke, because nothing was built against the limits
before this ticket.

**Targets.** A target is one string, the operating system and the architecture
joined by a hyphen, such as `linux-x86_64`, spelled exactly as
`std::env::consts::OS` and `std::env::consts::ARCH` spell them. `extract` takes
it as a plain `&str`, and nothing in `plugin-runtime` exports its derivation:
the tests pass explicit target strings, and `async-initialisation` owns the
helper that derives this host's target. The loader that selects a library and
the producer that writes a bundle must spell it the same way, because two
derivations that disagree would refuse a bundle that carries the library the
host needs. A bundle's library path per target is `lib/<target>/<file name>`,
the archive root carries `manifest.toml` plus one directory per target, and a
target directory holds exactly one file.

**Rules the landed ticket enforces and records in contract 17.8, in the order it
decides them.** Refuse an archive this build cannot read; refuse an archive
above the entry count limit; refuse an absolute entry name (a leading separator
or a Windows volume), a name carrying `..`, a name that is empty once its
separators are removed, or a name carrying a NUL byte; refuse a symlink, a
directory, or any other entry that is not a regular file, which covers a
hardlink, a device, a socket and a FIFO; refuse an entry that declares
permission bits other than `0600`, the mode the host itself writes, which is the
strict form of the declared-mode rule, since an entry that declares no mode is
accepted and no other mode is; refuse an entry above 64 MiB declared or an
archive above 256 MiB declared between its entries; refuse an entry this host
stages whose bytes or checksum do not read; and refuse an archive with no file
directly under `lib/<target>/`, or with more than one. Every entry is validated,
even when its target is not this host's, and only the root manifest and this
host's target directory are written to disk.

The one-file-per-target rule and the strict declared-mode rule narrow two of the
map's open fog items: the permission bits extraction accepts are fixed at `0600`,
and a v1 bundle carries no assets beside the manifest and the one library per
target, which a later ticket can relax.

Two refusals moved a ticket earlier than the plan placed them.
`MissingTargetLibrary` and `AmbiguousTargetLibrary` are extraction's, because
`library_path()` returns one path and only the archive can say whether one file
is there. `manifest-and-library` keeps its own refusal for a manifest that
declares no library for this host, so the two stay distinguishable and
`startup-policy` maps all three to its disable reason rather than collapsing
them.

`manifest_path()` may name a file that is not there: a bundle with no root
manifest still stages, and the refusal is deliberately left to

ordering at its own seam.

### `manifest-and-library` (feature, m)

**Exports.** `plugin_runtime::manifest`, declared as `pub mod manifest`, landed
as `crates/plugin-runtime/src/manifest.rs`. A `Manifest` value has private
fields, so `Manifest::parse` is the only way to obtain one and the value is
proof that the text it came from was the format. Its surface is:

- `Manifest::parse(text: &str) -> Result<Manifest, ManifestError>`, the text
  form. It takes the text alone and decides nothing about identity.
- `Manifest::read(staged: &StagedBundle, common_name: &str) -> Result<Manifest,
  ManifestError>`, the staged-bundle form. It tests that the staged manifest
  path resolves rather than assuming it, reads the text, parses it, and compares
  the declared `name` against the chain's leaf common name. The caller passes
  that name, because `StagedBundle` does not carry it: it comes from
  `VerifiedBundle::leaf_common_name()` at the verification step.
- The named accessors `name()`, `version()`, `abi_major()`, `min_abi_minor()`,
  `libraries()`, `capabilities()` and `config_schema()`, which keep the fields
  private while a dependent reads them.
- `Manifest::select_library(&StagedBundle, target: &str) -> Result<PathBuf,
  ManifestError>`, which resolves only this host's declaration against the
  staging directory and answers the path, or the refusal that it is not there.
- `Manifest::abi_check() -> Result<(), MetisAbiError>`, the manifest's ABI
  demand read from the plugin's side. The declared `abi_major` must equal this
  build's major, and this build's minor must not be below the declared
  `min_abi_minor`. A requirement older than this build's minor is legal and
  served; a newer one is refused. That is the direction parent decision
  `compatibility-policy` C4 fixes, and this check is this ticket's bundle-load
  gate on the minor bump. An older table is still refused by the landed table
  gate before any entry is read.
- `ManifestError`, six struct variants in the crate's existing error style
  (`CallError`'s shape: a plain enum, `Display`, `std::error::Error`, no panic

  `LibraryNotStaged` and `NameMismatch`. `Manifest` is `PartialEq` and not `Eq`,

- The mapping step, `unsafe Loaded::open(path, &Manifest) -> Result<Loaded,
  CallError>`, which carries the same obligation as the landed `Loaded::load`

  `manifest.abi_check()?` first and then delegates to the unchanged

The load entry landed as a plain `async fn` with the host first:

```rust
pub async fn load_bundle(
    host: &Host,
    bundle_path: impl AsRef<Path>,
    config: &serde_json::Value,
    host_context: &serde_json::Value,
    trust: &TrustStore,

```

It composes `std::fs::read`, verification, extraction, manifest validation,
library selection, the ABI check, the initialisation call, the capability
cross-check and registration. The host parameter is not decoration. A failed
load returns no `Serving`, so the host is the only thing a caller can read the
initialisation ordering from, and a sink is set when the host is built, which is
what lets `callback-sink` observe callbacks and `sample-bundle-ci` observe an
event through the installed sink. `startup-policy` owns building the host it
passes. The future is still caller-driven, so the caller's runtime decides when
plugin code runs.

`Serving` carries the registered instance name, the `Arc<Instance>`, the
descriptor list it registered, and the registry it was registered in:
`name()`, `instance()`, `capabilities()` and `registry()`. The entry builds one
fresh `Registry::new()` per load and registers the instance into it, so
`Serving::registry()` is the registry that routes a call to that instance.
`teardown-and-release` reaches `Registry::unregister` and the enable and disable
state through `Serving::registry()`, and a daemon that wants one registry for
several plugins registers each `Serving` into its own aggregate registry through
the same `Registry::register`, which stays the one registration path. No second
registry type and no second registration path landed.

The configuration and the host context are built by the daemon and delivered in
one payload, and `plugin-runtime` does not own their value types: the landed

feature gate, which the dependency posture keeps off for this crate. What landed
is `&serde_json::Value` for both parameters, and `initialisation_body` builds the
one `{"config", "host_context"}` object with `json!` from two private
constants, `CONFIG_FIELD` and `HOST_CONTEXT_FIELD`, which are the only place
those two names appear. `Initialisation` and `HostContext` are therefore
unreachable from the runtime, and the host context's field set is kept in step
with contract section 18 by hand rather than by the type. That duplication is
the price of the unchanged dependency posture and is this ticket's recorded
choice rather than an open question; the daemon, `startup-policy` and
`sample-bundle-ci` build the same two names and their own value shapes. The
plugin's setup failure falls into two classes the caller can tell apart, and
they are separate values rather than one status the caller interprets: the
plugin is defective, or the configuration does not match what the plugin
declared. The fixture gained one public constant,
`plugin_fixture::DEFECTIVE_INITIALISATION`, a reserved instance name that makes
the fixture's own `init` fail with `Internal` so the plugin-defect class is
reachable from a real bundle; no other struct literal changed and the ABI
harness stays at its 82 checks.

The capability cross-check compares capability names only. The two declarations
are walked as name sets, the manifest's list first and then the library's, so a
disagreement with several members reports the first difference in that order and
the refusal names the capability that differed. Kind, version and schemas are
not compared, which is a deliberate decision recorded in contract 17.9: the
manifest's schemas are declared text an author writes while the library derives
its own, so comparing them would refuse a bundle the format is meant to allow,
and a capability's kind and version are gated where a call routes. A schema
drift between the two sides is therefore not caught at load, and that is what
makes `sample-bundle-ci`'s hand-written manifest reachable at all.

Four landed facts shape this ticket. The initialisation call is
`Loaded::init_plugin(&host, body) -> Result<PluginInit, CallError>` plus the
public `PluginInit` future and `CallError::Init`, which was `CallError::Create`,
so this ticket drives that surface rather than reaching the raw table. The
mapping step is the landed `unsafe Loaded::open(path, &Manifest)`, which carries
the same obligation as `Loaded::load` because it maps arbitrary native code, so
the load entry contains one `unsafe` block whose justification is the trust the
bundle's signature verification established and the extraction that staged the
file; `open` decides the manifest's demand with `abi_check` before it delegates
to `Loaded::load`. The load entry confirms at its own seam that the failure
ordering is the contract's, which the earlier landings covered only at the raw
ABI seams, in `crates/plugin-contract/src/authoring/` and in the ABI harness
against the C plugin. The derivation of this host's target is this ticket's too,
because `bundle::extract` takes a plain `&str` and nothing exports a helper: it

### `call-cancellation` (feature, m)

The cross-cutting decision this ticket serves is ADR 0005's caller-owned
cancellation (`docs/adr/0005-plugin-host-boundary.md`): the caller owns the
deadline and the drop, the runtime holds no timer and no default deadline, and
the same rule reaches teardown. This section records the landed surface and does
not restate the decision.

**Exports.** `Instance::cancel_all(&self, deadline: std::time::Instant) ->
CancelReport`, plus two new public types at the crate root:

```rust
pub struct CancelReport {
    pub deadline: Instant,
    pub cancelled: Vec<u64>,
    pub refused: Vec<RefusedCancel>,
}
pub struct RefusedCancel {
    pub request_id: u64,
    pub status: MetisStatus,
}
```

The deadline is `std::time::Instant`, the caller's own monotonic reading, named
back in the report rather than armed: the runtime holds no timer and no default
deadline. `cancelled` is sorted ascending by request id, so one state yields one
report, and `refused` carries the frozen status each id answered. The call is
synchronous. It cancels a snapshot of the instance's in-flight set and waits for
nothing, so a call started after the pass is not in the report and the caller's
own loop owns that case. `teardown-and-release` takes the same `Instant` type.

**The in-flight gate, which is a behaviour change and not only a refusal added.**
`Instance::cancel` and `Instance::complete_service` answer
`Err(CallError::Status(MetisStatus::NotFound))` before entering the plugin when
the id is not in this instance's own in-flight set. The plugin's call registry is
process-wide, so before this landing an id held by another instance reached the
plugin and could mark that instance's call. The landed `NotFound` is therefore
the expected answer rather than an error to report for three dependents:
`callback-sink` answering a service whose call was already released,
`teardown-and-release` cancelling or draining a pass where ids finish meanwhile,
and a daemon answering an id it does not hold. A second cancel of a live id is
still accepted. The token-marking step is the private `mark_cancel`, typed as the
frozen `MetisStatus` alone, and `cancel_all` loops over it rather than over
`Instance::cancel`, because the report has no error variant of its own to invent.
`Host::cancel_services(request_id)` is the drop rule's host-side entry and is
crate-private, so no daemon-facing surface grew.

**The drop rule, in the order it runs.** `PluginCall::drop` releases the
host-held service-request copies for this call through the crate-private
`Host::cancel_services`, appends the ledger line for them when there were any,
appends the unacknowledged-cancel line when the plugin accepted a cancel and no
poll observed the terminal `Cancelled` status, drops the plugin's future, and
appends the reclaim line. "Every buffer the host still holds for the call" is the
host-held copy of each outstanding service-request payload: per contract section
11 rule 1 every plugin-allocated buffer is copied and released at the callback
that carried it, so a live call leaves none in the host's hands, and the wider
reading has nothing to release. The two ledger lines are, each only when it says
something: `call <id> released <n> service request(s) the host still held` and
`call <id> cancel unacknowledged: the plugin never resolved it as cancelled`. An
unacknowledged cancel does not quarantine, and the instance keeps serving.

**Existing abstractions to use.** `Instance::cancel` and the in-flight set,
`Instance::complete_service`, the ordering ledger, the frozen `MetisStatus`
space, the fixture's cancellation token, and `Instant`, which the ABI harness
already uses, so the crate has one deadline representation rather than two. The
one new piece of host state is `Instance::accepted_cancels`, because only a poll
observes the terminal status and that is the call's own fact rather than the
instance's.

**Do not reimplement.** No timer, no runtime, no new status variant for
cancellation. Do not add a quarantine path for a slow call: quarantine stays
reserved for an abandoned poll and an unreleasable teardown. The do-not list held
in full, and no dependency, ABI artifact or contract text changed.

**Seams.** One product seam: `crates/plugin-runtime/tests/cancellation.rs`, 422
lines and six cases, against the public instance and call API with a cancellable
fixture capability, the ordering ledger and the plugin's own callback logs as the
assertions. `docs/testing.md` gained the command bullet for the new file. Two of
the six cases are shape or regression assertions rather than RED-first cycles:
criterion 1's behaviour was already landed by `waker-lifecycle-fix`, and criterion
6 is a property of the code's shape (the case proves `cancel_all` coerces to
`fn(&Instance, Instant) -> CancelReport`, which is what shows the form is
synchronous and deadline-fed), so neither could have a failing first run, and the
worker recorded that rather than claiming one.

### `callback-sink` (feature, m)

The cross-cutting decision this ticket serves is ADR 0005's one sink carrying
every callback (`docs/adr/0005-plugin-host-boundary.md`), set when the host is
built, infallible and non-blocking, naming its instance, with a host that has no
sink still legal. This section records the landed surface and does not restate
the decision.

**Exports.** `plugin_runtime::sink`, landed as
`crates/plugin-runtime/src/sink.rs`, with one trait and one typed log level:

```rust
pub trait Sink: Send + Sync + 'static {
    fn progress(&self, instance: &str, request_id: u64, payload: Vec<u8>);
    fn event(&self, instance: &str, topic: &str, payload: Vec<u8>);
    fn log(&self, instance: &str, level: LogLevel, message: &str);
    fn service_request(
        &self,
        instance: &str,
        service: &str,
        request_id: u64,
        payload: Vec<u8>,
    ) -> MetisStatus;
}
```

`LogLevel` is `Debug`, `Info`, `Warn` and `Error`, with `from_abi(i32) ->
Option<LogLevel>` (a fifth level is a protocol violation, never invented),
`to_abi()` and `as_str()`. Every method is infallible and must not block, because
it runs inside the plugin's poll frame. Every callback names the instance;
progress and a service request carry the request id, an event carries its topic
and payload and no request id, because the frozen ABI callback has none, and a log
carries its typed level. A service request's return value is the status the ABI
expects, and an accepted request is answered later through the existing
`Instance::complete_service`. The sink is set at `Host` construction with
`Host::with_sink(sink)`. `Host::for_instance(instance)` is the second landed
public item and the only way to name an instance on the raw path: the ABI carries
one opaque pointer per host table, so the name has to travel in the table an
instance was built with. It shares the sink, the records and the ordering ledger
with the host it came from, and the load entry applies it with the manifest's name
for every bundle, so `startup-policy`, `teardown-and-release` and
`sample-bundle-ci` need none of it. A caller that drives `Loaded::init_plugin` by
hand without it delivers the empty string as the instance name.

**Contract decisions a dependent cannot infer from the trait.** A sink is handed
the decoded body, with the ABI's one-byte envelope stripped, because progress,
event and service-request bodies are enveloped on the wire and the log message is
the topic and message string itself; the runtime already strips the envelope for
call responses and capability lists. A host built with `Host::with_sink` answers
nothing through `logs()`, `events()`, `pending_services()` and `take_service()`,
because the recording default owns that storage and `Records` is crate-private:
a consumer that wants both a destination and the accessors implements its own
recording sink, and `sample-bundle-ci` therefore reads events through its sink and
not through the accessors. Delivery is ordered per instance by a per-instance
delivery lock, so two instances' callbacks are not ordered against each other.

**The recording default, the refusals and the lock discipline.** `Host::new()`
installs the private `RecordingSink` over a private `Records`, which is the
storage the accessors read, so a host with no sink keeps its behaviour and no
existing test or the ABI harness changed. A buffer that is not one of this
build's payloads, and a log level outside the four, are recorded on the ordering
ledger and nothing is delivered. A panic inside a sink is caught in the
callback's own frame and recorded on the ordering ledger while the plugin's call
still completes and the instance keeps serving. One `lock` helper in `lib.rs`
takes a poisoned mutex's contents, and every host-side lock in the crate goes
through it, so a contained panic does not become a second panic on the next read
of the same state; that is a behaviour change for every locked path in the crate,
not only the sink's, and it is what makes a recorded sink panic readable.

**The panic-free check, with its measured scope.** `no-panic` 0.1 is an optional,
feature-gated, build-time dependency behind the crate feature `no-panic-check`,
off in every shipped and default build, so the resolved graph is unchanged there;
the workspace profile `no-panic` (`inherits = "dev"`, `opt-level = 1`) is the one
place the optimization the check needs is set. The CI step `Plugin host callback
panic-free check` runs `cargo test --profile no-panic -p plugin-runtime --features
no-panic-check --no-run`, which is command 11 of `docs/testing.md`. The measured
scope is narrower than the plan's sentence, and the plan's sentence is superseded:
the four ABI frames `host_progress`, `host_emit_event`, `host_log` and
`host_service_request` carry the attribute and are hand-offs to `deliver_*` frames
of the same shape, because a frame passes the assertion only when every unwinding
path in it is one a caught closure holds, while a frame that locks a `std` mutex,
drops an allocation or drops a caught panic payload fails it. The waker frames,
the poll and drop wrappers and the buffer release path are not annotated, so the
per-frame `catch_unwind` remains the runtime guarantee and this check is an
addition to it. `docs/testing.md` records the two profiles in which the check
proves nothing, one that never links the frame and one that does not unwind.

**Existing abstractions to use.** `Host`'s existing recorded callbacks and
accessors (`logs`, `events`, `pending_services`, `ordering`) became the default
sink's storage rather than a second path, so the existing tests and the ABI
harness do not change. `catch_unwind` with `AssertUnwindSafe`, as the rest of the
crate already does. A plain enum for the log level in the Rust API, with the
integer mapping at the ABI edge.

**Do not reimplement.** No queue and no backpressure in the runtime: a daemon
that wants either puts it behind the sink. No second callback path for logs. Do
not let the sink call back into the runtime or the plugin. The do-not list held in
full, and no ABI type or contract text changed.

**Seams.** One product seam: `crates/plugin-runtime/tests/sink.rs`, 937 lines and
10 cases, covering each callback kind with its instance name and fields, the
payload copy outliving the plugin's buffer including when the sink panics, the
panic record on the ledger, per-instance ordering, the service round trip, the
unchanged accessors on a host with no sink, and a bundle loaded through the load
entry delivering to the sink the caller installed. The fixture's buffer ledger is
process-wide, so every case in that binary takes one file-wide lock. One
build-level check: the CI step above. No pre-existing test file is in the diff,
which is what makes "the existing tests pass unchanged" checkable.

### `startup-policy` (feature, m)

The cross-cutting decision this ticket serves is ADR 0005's three start-up
outcomes and their split by the single predicate `BundleError::is_trust_failure`
(`docs/adr/0005-plugin-host-boundary.md`), which is also contract section 19.
This section records the landed surface and does not restate the decision.

**Exports.** `plugin_runtime::startup`, landed as
`crates/plugin-runtime/src/startup.rs`:

```rust
pub async fn start_plugins(
    dir: impl AsRef<Path>,
    config: &Map<String, serde_json::Value>,
    trust: &TrustStore,
) -> Result<StartupReport, StartupStop>
```

It returns a `Result` rather than a report alone, because a stop has to return in
place of one, and it is `async` because it awaits every load. The plan's
`start_plugins(dir, config, trust) -> StartupReport` could not express the
ticket's own stop rule and is superseded. `StartupReport` carries `host()`,
`serving()`, `disabled()`, `offered_capabilities()` and `async call(&self,
qualified: &str, body: &[u8], request_id: u64) -> Result<Vec<u8>, RouteError>`.
`DisabledPlugin` carries `name()`, `reason() -> &LoadError` and `capabilities()`,
where the reason is the load's own typed error rather than a restatement of it.
`StartupStop` carries `path()` and `error()` and implements `Display` and
`Error`; `teardown-and-release` then widened it with `serving()` and
`into_serving()` and narrowed its derives to `Debug`, recorded under
`## Level 5`.

**The directory discovery rule.** Every regular file directly in the directory is
one bundle, named by its file's stem, sorted, with no recursion and no discovery
file. An entry that is not a regular file is skipped. A directory that cannot be
listed is a stop, carried as `LoadError::Unreadable` for the directory itself.

**The classification, exactly as landed.** The policy classifies by variant, not
by the status inside one, through one private predicate:

| `LoadError` | start-up outcome |
| --- | --- |
| `Trust` whose `BundleError::is_trust_failure()` answers true | stop |
| `Unreadable`, `UnloadRefused` | stop |
| `Manifest` carrying `Absent`, `Unreadable`, `Invalid` or `NameMismatch` | stop |
| `Trust` whose `is_trust_failure()` answers false, which is a container this build cannot read | disable |
| `Stage`, `Call`, `CapabilityMismatch`, `Registration` | disable |
| `Manifest` carrying `NoTargetLibrary` or `LibraryNotStaged` | disable |
| `ConfigurationRefused`, `PluginDefect` | disable, as a placeholder, after the instance is unloaded |

The file's `Manifest` rows refine the level-3 sentence that stood in this
section. `LoadError::Manifest` is split finer than "an absent or invalid manifest
stops start-up": the four refusals that mean the bundle's declaration is not what
the chain carries stop, while the two that mean this host has no library it can
use only disable that one plugin. The coarse level-3 sentence is therefore
superseded, and the level-3 table now points here. The four library refusals,
two from extraction (`StageError::MissingTargetLibrary` and
`StageError::AmbiguousTargetLibrary`) and two from the manifest
(`ManifestError::NoTargetLibrary` and `ManifestError::LibraryNotStaged`), share
one disable reason with four distinguishable names, and the report names which
one refused. `ManifestError` has six variants, of which the plan named neither
`Unreadable` nor `NameMismatch`, so both error sets are classified as values
rather than matched exhaustively. A refused unload during a failed
initialisation's recovery stops start-up, because continuing would leave the
daemon holding an instance it cannot describe, which is the effort spec's stories
41 and 42 read at the load seam: a plugin whose initialisation fails is unloaded
and replaced by a disabled placeholder, so the failure is visible and the library
is gone.

**A placeholder is not registered; the report answers it.** `StartupReport::call`
answers a declared capability of a disabled plugin from the private
`disabled_capability` lookup before it delegates to each serving plugin's own
registry. The lookup matches the placeholder's name as a prefix and then requires
the remainder to be a declared capability, so a dotted placeholder name stays
unambiguous and an undeclared name under it still answers `Unknown`. There is no
placeholder registry, so the sentence that placeholders "need a registry of their
own" is superseded rather than satisfied: one routing path remains, and a daemon
that wants one registry for everything registers its placeholders itself.
`teardown-and-release` must not expect to find a placeholder in a `Registry`, and
nothing here unloads one, because a failed load never produced a library to
unload.

**One host per pass, one registry per plugin, no aggregation.** The policy builds
one `Host::new()` and passes it to every load, so a directory holding bundles from
different producers can reach the host's one-host-one-library refusal, which warns
on stderr and is recorded rather than fixed. Each `Serving` keeps the registry its
own load built, so a duplicate plugin name across two bundles is not refused here.
Aggregation belongs to `teardown-and-release`. The host context is built inside
the policy as `{"instance_name": name, "capability_version": 1}` with no
`data_dir`, so no caller can make two plugins claim one name.

**The configuration key, settled by the contract.** The initialisation payload
is built before the load runs, so the only name available then is the bundle
file's stem: both the configuration lookup and the host context use it. Contract
section 19 now states the rule, and it is the source: a bundle's identity before
its manifest is read is its file's stem, the daemon resolves configuration by
that name, and a placeholder whose manifest could not be read is named by it;
once the manifest is readable, the name the manifest declares is the
registration and routing identity. A manifest's name is known only after the
load or the placeholder re-read, so a placeholder can carry a manifest name that
differs from the key its configuration would have used. A daemon must therefore
key its configuration by file stem, or name its bundle files after its plugins,
and `sample-bundle-ci` follows the same rule. The earlier sentence that called
this a caller contract, and the recorded resolution's wording (the name the load
reports), are superseded by contract section 19.

**The placeholder path's cost.** A load that refused hands back no `Manifest`, so
the placeholder path reads the bundle a second time: `verify_bundle`,
`bundle::extract` and `Manifest::read`, with the crate-private `host_target()`
reused rather than derived a third time. Any refusal along the way answers the
file-derived name with no capabilities, which is the case for a bundle whose
container version this build does not know. The second read is the cost the
recorded resolution accepted for leaving the level-3 load surface unchanged (its
option A), and it runs only for a bundle that was disabled, never for one that
started.

**Existing abstractions to use.** `BundleError::is_trust_failure()` for the
trust half of the split, called as a predicate rather than by matching
`BundleError` variants; `LoadError` for the per-plugin outcomes, classified by
variant; `Registry`'s existing entry and route-error surfaces for the
placeholder's answer; and the `&Host` that `load_bundle` takes as its first
parameter, built by the policy. A placeholder named from a manifest whose name
carries a dot routes like any other entry, which is the rule
`dotted-instance-names` landed: `Registry::route` takes the tool half from the
owner the routing map returned for the exact key, so a dotted name and its
undotted neighbour keep separate namespaces. The policy itself is a table in the
crate, documented in `docs/plugin-contract.md` section 19.

**Do not reimplement.** No second registry and no second route error. Do not turn
a trust failure into a placeholder, and do not turn a container this build cannot
read into a stop. A bundle file that cannot be read at all is a different case:
the landed `LoadError::Unreadable` stops start-up, and that is what the split
above fixes. Do not scan the filesystem recursively or invent a discovery format
beyond the plugin directory. The do-not list held in full.

**Seams.** One product seam: `crates/plugin-runtime/tests/startup.rs`, 1031 lines
and 21 cases, over a temporary directory the test owns, holding a mixture of good
bundles and one per refusal kind, so the name the policy knows a bundle by before
its manifest is read and the name the manifest declares can be told apart. The
unknown container version case is the only refusal that degrades without its
manifest ever being read. The stop-on-refused-unload case is driven by a fault
cdylib the test compiles itself from `tests/fixtures/refusing_destroy.rs`, with
the new `compiled_fixture` support helper, and the one landed assertion in
`crates/plugin-runtime/tests/registry.rs` that matched the old `Disabled` tuple
form was adapted mechanically. The test file carries its own directory, chain and
manifest harness, because `support/bundle.rs`'s manifest writer hardcodes one
plugin name, so parameterising the shared writer by name would remove the
duplication. Criterion 6 is satisfied by prose (contract section 19, the
discovery rule and the three-outcome table), matching the landed precedent for
documentation criteria. Contract section 19 and the new command bullet in
`docs/testing.md` are the documentation halves.

### `teardown-and-release` (feature, m)

**Exports.** The plan fixed `Serving::release(deadline: std::time::Instant) ->
ReleaseReport`. The landed entry consumes the `Serving` and is asynchronous:

```rust
pub async fn release(self, deadline: std::time::Instant) -> ReleaseReport
```

It unregisters the instance, cancels or drains in-flight calls to the caller's
deadline, calls the plugin's shutdown entry, drops every future, destroys the
instance, unloads the library, and reports the ledger entries added, in that
order. The await is what lets it drain: the runtime hands each `PluginCall` back
to the caller and keeps no handle on it, so "drop every future" is the caller's
own drop and the release can only wait for it. The wait is a `poll_fn` that wakes
once and returns `Pending`, with the deadline read in the loop condition, so the
loop yields instead of spinning the caller's thread, and the crate still arms no
timer and holds no default deadline. A caller that never drops a call reads
`ReleaseRefusal::FuturesInFlight` at its deadline rather than a hang. The
deadline is the same `std::time::Instant` the landed `Instance::cancel_all`
takes, which is the coherence the level-4 landing left open, and the report is
the caller's record rather than a wait of the runtime's. An instance that cannot
be released stays mapped and is reported, which covers a shutdown that returns a
non-ok status, a quarantined instance whose abandoned poll never returns, and an
unload refused for any reason. The daemon's shutdown deadline ends the wait and
produces the report.

**The report types.** Two new public types landed at the crate root beside
`Serving`, `ReleaseReport` and `ReleaseRefusal`, because the plan fixed only the
signature and described the report's content in prose:

```rust
impl ReleaseReport {
    fn name(&self) -> &str;
    fn deadline(&self) -> Instant;
    fn cancelled(&self) -> &CancelReport;
    fn released(&self) -> bool;
    fn refusal(&self) -> Option<&ReleaseRefusal>;
    fn resident(&self) -> Option<&Arc<Loaded>>;
    fn ledger(&self) -> &[String];
}
pub enum ReleaseRefusal {
    Quarantined,
    FuturesInFlight(Vec<u64>),
    Shutdown(CallError),
    Unload(CallError),
}
```

`ReleaseReport` implements `Display`, and `ReleaseRefusal` carries `step()`,
`Display` and `Error`. `resident()` is the library reference the release keeps
when the instance could not be released, so that instance's library stays mapped
after the report is read, and it is the only remaining handle to it.
`ReleaseRefusal::step()` names `unload` for a quarantined instance, because the
step a quarantine refuses is the unload, and `drain` for calls still in flight.
The spec named no step vocabulary before this landing, so that wording is this
ticket's.

**Disabling and enabling.** They are registry state only and touch neither
in-flight calls nor the library: they refuse or accept new calls, and enabling
needs no reload. The plan's path, each `Serving::registry()`, could not serve the
criterion, because `Registry::enable` takes `&mut self`; the additive
`Serving::registry_mut(&mut self) -> &mut Registry` is the landed path and the
surface a daemon toggles a plugin with. `registry()` is unchanged and
`StartupReport::call` still uses it.

**The fixture's part.** `plugin-fixture` gained the reserved instance name
`REFUSING_SHUTDOWN` (`fixture-refusing-shutdown`) and its one field, whose
teardown raises the panic the authoring adapter contains. The authoring `stopped`
hook is infallible, so that panic is the only route to a shutdown entry that
answers a status other than `ok`. The name joins the existing
`DEFECTIVE_INITIALISATION` convention; a hand-written fault cdylib was rejected
in its favour.

**What the level-4 landings hand it.** Three things this ticket must follow.
`Serving::registry()` is read per serving plugin, because `start_plugins` keeps
one registry per `Serving` and does not aggregate them, and a placeholder is not
in any registry, so the release path never looks for one there and never unloads
one. Cancelling or draining will answer the frozen `NotFound` for ids that
finished during the pass, which is the call-cancellation in-flight gate read at
this seam, and the ledger the report names will carry the two cancellation lines
`call <id> released <n> service request(s) the host still held` and `call <id>
cancel unacknowledged: the plugin never resolved it as cancelled`. And a caller
that composes the two surfaces handles `start_plugins`'s `Result`: a stop returns
no `StartupReport`, and the landed answer to the dropped-`Serving` gap is a
hand-over rather than a release inside the policy. `StartupStop` carries the
`Serving` values a pass started, in start order, through `serving()` and
`into_serving()`, and unloads nothing on that path, so the caller releases what
it is handed. Release-on-stop with an immediate deadline was rejected because the
deadline is the caller's and the runtime holds no timer and no default. That
landing narrowed `StartupStop`'s derives from `Debug, Clone, PartialEq, Eq` to
`Debug`, with a manual `Debug` for `Serving`, so a caller that cloned or compared
one must adapt; nothing in the tree did, and the startup tests were updated.

**Existing abstractions to use.** `Instance::unload`, `Instance::shutdown`,
`Instance::cancel_all(deadline: Instant)` and its `CancelReport`, the ordering
ledger, `instance.is_quarantined()`, `Serving::registry()` for
`Registry::unregister` and the additive `Serving::registry_mut()` for
`Registry::enable`, because the load entry registers each instance into a
registry of its own, and the landed
`LoadError::UnloadRefused { plugin, step, status }`, which is the typed outcome a
refused `destroy_instance` already answers on the load path. The unload guards
stay: the in-flight set, the last `Arc`, and the rule that the table is dead after
`destroy_instance`, as the hazard findings settled. No outstanding-clone gate is
added, and that typed refusal does not imply one.

**Do not reimplement.** No clone counter and no outstanding-clone gate. No
forced unmap of a library that might still run. No live teardown or
reconfiguration: unload happens at shutdown.

**Seams.** One product seam: the awaited `Serving::release(self, deadline)`, the
public instance and report surface, and the ledger as the assertion, tested from
`crates/plugin-runtime/tests/teardown.rs`, 842 lines and nine test functions, of
which a run passes eight and ignores one. The ignored one is the faulting child
the drop-after-unload case spawns as a subprocess of its own test binary and
reads as the signal the child died with, because the behaviour under test is a
fault; the case asserts `SIGSEGV`, matching the hazard prototype's method, is
Unix-gated, and prints `[skip]` and returns off Unix, following the pipe test's
convention. On this Linux host it ran for real and the child's marker line
proves the fault happens after the unload. Four cases had no failing first run,
because the whole refusal set landed with criterion 1's slice; sensitivity was
proved by mutation instead, where removing the drain loop fails criteria 1 and 5
and removing the quarantine gate fails criteria 3 and 5, matching the
`call-cancellation` precedent for a criterion that could not be RED first.
`docs/testing.md` gained the teardown command bullet and one sentence on the
startup bullet. No `docs/plugin-contract.md` edit: contract section 11 rule 7
already states the teardown order.

**Interface contract.** `Serving::release(self, deadline: Instant).await`,
`ReleaseReport`, `ReleaseRefusal` and `Serving::registry_mut()` are consumed by
`sample-bundle-ci` and by a daemon composing the start-up pass. Each call site
awaits the release on an owned `Serving` and drops its own calls, which is what
completes the drain, and a caller that handles `StartupStop::into_serving()`
releases each `Serving` it is handed.
