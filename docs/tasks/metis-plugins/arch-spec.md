# arch-spec, metis-plugins

Effort-wide architecture spec, shared by every ticket chain in this effort. Each
section below gives one pending ticket its planned public surface, the existing
abstractions it must build on, what it must not reimplement, the seams the
tdd-worker tests at, and the interface contract its dependents call. The
spec-reconciler folds each landed ticket's committed deviation report back into
this file, one editing pass per level, and the doc-gate on this repo's prose
applies here too: no em-dashes, plain vocabulary, the glossary's terms.

## Source of truth for the target state

- Architecture and plan: `docs/rough-plan.md`.
- Effort destination, decisions, fog: `docs/tasks/metis-plugins/map.md`.
- Effort spec, the user story set and the implementation decisions:

- Prior art in tree: `spikes/plugin-abi-mechanics/` (the table, the payload
  envelope and the header generator), `spikes/plugin-authoring-trait/` (the

- Frontier: `tw_frontier metis-plugins`.

## Shared conventions

- Branches: landing branch `task/<ticket-slug>`, working branch
  `ticket/<ticket-slug>` created off it, merged back with `--no-ff` and
  deleted. Chains land in dependency-level order, and levels are strict
  barriers.
- Toolchain: devenv only. Every command runs as `devenv shell -- <command>` on
  the toolchain `devenv.nix` pins: Rust nightly, edition 2024,
  `resolver = "3"`.
- Gates, always and in this order: `cargo fmt --check`,
  `cargo clippy --all-targets -- -D warnings`, `cargo test`. The effort's own
  contract and ABI commands are numbers 3 to 7 of `docs/testing.md`.
- Every crate carries `[lints] workspace = true`. New third-party dependencies
  are added once to `[workspace.dependencies]` in the root `Cargo.toml` with a
  comment that says why, and crates reference them as `.workspace = true`.
- Generated artifacts are never hand-edited. The ABI header
  (`crates/plugin-contract/include/metis_plugin_abi.h`) is regenerated by
  `bash scripts/regenerate-abi-header.sh`, and the check form fails when the
  generated file and its source disagree.
- Names fixed already and not to be changed: crate `plugin-contract`, crate
  `plugin-runtime`, crate `plugin-fixture`, entry symbol
  `metis_plugin_entry_v1`, feature gate `authoring`, table type
  `MetisPluginTableV1`, ABI major 1.
- Prose and comments follow `AGENTS.md`: no em-dashes anywhere.

## The landed baseline

What exists today, and therefore what every ticket below builds on.

- `crates/plugin-contract`: the versioned C ABI. ABI major 1, minor 1.
  `MetisPluginTableV1` carries eight slots, `create_instance` first and
  `service_complete` last, with the slot constants, thresholds and layout
  assertions in `src/abi/layout.rs`. `METIS_PLUGIN_ENTRY_V1` names the entry
  symbol. `src/payload.rs` writes and reads the UTF-8 JSON envelope.
  `src/authoring/` holds the Rust authoring surface behind the `authoring`
  feature: the `Plugin` trait, the export adapter, the call and waker bridge,
  and the buffer ownership helpers.
- `crates/plugin-runtime`: the host side. `Loaded` maps a cdylib and reads the
  table through the version gate, `Host` carries the host table plus the
  recorded callbacks, `Instance` owns one instance and its in-flight set,
  `PluginCall` is the polled future, `registry::{Registry, Entry, RouteError,
  RegistryError}` routes and validates. Its error surface is settled: one type
  each for load and dispatch (`CallError`), routing and validation
  (`RouteError`) and registration (`RegistryError`).
- `crates/plugin-fixture`: the Rust fixture, its hand-written C twin
  (`c/c-plugin.c`), the other-major plugin, and the ABI harness
  (`src/bin/abi-harness.rs`) that hand-drives a real host.
- `docs/plugin-contract.md` is still v1 text. It names `create_instance` and a
  counters entry that this effort's spec removes. The two amendments land in
  `abi-initialisation-entry` and in `bundle-verification`, in that order, and
  no earlier ticket edits that file.
- `docs/testing.md` is the command protocol. Tickets that add a command or close
  a recorded gap edit it in the same commit.

## Cross-ticket interface contracts

The chain of surfaces the effort builds, in dependency order. Each later ticket
consumes exactly the surface its predecessor exported, and nothing else.

```text
verify_bundle(bytes, &TrustStore) -> Result<VerifiedBundle, BundleError>   bundle-verification
staged = extract(verified, host_target) -> Result<StagedBundle, StageError> bundle-extraction
manifest = Manifest::parse(text, &CapabilityList) -> Result<Manifest, ..>   manifest-and-library
loaded = Loaded::open(lib_path, &Manifest)                                  manifest-and-library
serving = load_bundle(path, config, ctx, trust) -> Result<Serving, ..>      async-initialisation
instance.cancel_all(deadline) -> CancelReport                               call-cancellation
Host::with_sink(sink)                                                       callback-sink
start_plugins(dir, config, trust) -> StartupReport                          startup-policy
serving.release(deadline) -> ReleaseReport                                  teardown-and-release
pack-sample-bundle + one end-to-end CI test                                 sample-bundle-ci
```

## Level 0

### Required state before the dependency levels: the ABI and the waker

`waker-lifecycle-fix` (bug) and `bundle-verification` (feature) are the two
independent, unblocked tickets. The bug sits in `plugin-contract`'s authoring
bridge and in the host waker in `plugin-runtime`; the feature adds the bundle
verifier to `plugin-runtime`. Neither depends on the other, and both must land
before the rest of the graph.

The bug's interface contract, because `abi-initialisation-entry` depends on it:
the authoring bridge must hand a poll a `MetisWaker` whose lifetime the host
owns, so that the host releases exactly one owning reference when the poll
returns; `CallState` must carry the request id so a `wakes_after_drop` record
can name the call; and `waker_wake` must consume an owning clone at most once,
so a second wake on one clone cannot over-release. The fix is in
`crates/plugin-contract/src/authoring/call.rs` and `future.rs` plus the host
waker in `crates/plugin-runtime/src/lib.rs`, with the record rule worded in
`docs/plugin-contract.md` section 11 rule 4 as a counted violation rather than
an ordering-ledger entry. The measured reference counts and the three defect
statements are in the hazard findings file, not to be re-derived.

#### `bundle-verification` (feature, l)

**Exports.** A new `plugin_runtime::bundle` module, re-exported from the crate
root.

- `TrustStore`: the trust policy as a plain value the daemon constructs. It
  carries the root keys and the revocation list, each a set of key ids with the
  public key alongside. `TrustStore::empty()` is the compiled-in default the
  daemon starts from. The runtime never reads a configuration file and never
  defines the configuration file's shape.
- `BundleHeader`: the parsed fixed-size container header. Big-endian throughout,
  fixed width because the signature's location depends on it.
- `VerifiedBundle`: a borrowed view of an accepted bundle, carrying the header,
  the parsed chain, the leaf-authorising certificate's common name, and the
  archive bytes. Nothing is copied, and nothing is extracted.
- `BundleError`: one variant per refusal rule, in this crate's existing error
  style (`CallError` and `RouteError` are the models: a plain enum of struct
  variants, `Display`, `std::error::Error`, no panic path).
- `verify_bundle(bytes: &[u8], trust: &TrustStore) -> Result<VerifiedBundle<'_>,
  BundleError>`: the one entry point.

**The container, as this spec fixes it, so a second implementation can be
written from the contract alone.** A 40-byte header, then the chain region, then
the signature, then the ZIP bytes, and the file length equals signature offset
plus signature length plus ZIP length, so no byte escapes the signed range.

| offset | size | field |
| --- | --- | --- |
| 0 | 8 | magic, the ASCII bytes `METISBND` |
| 8 | 2 | container format version, `u16`, must equal this build's exactly, currently 1 |
| 10 | 2 | signing suite, `u16`, currently 1 for X.509 over Ed25519 |
| 12 | 2 | header length, `u16`, must equal 40 |
| 14 | 2 | reserved, `u16`, must be zero |
| 16 | 4 | chain length, `u32` |
| 20 | 8 | signature offset, `u64`, must equal header length plus chain length |
| 28 | 4 | signature length, `u32` |
| 32 | 8 | ZIP length, `u64` |

The **signed message** is the domain tag, then the header bytes, then the chain
bytes, then the ZIP bytes, with the signature bytes themselves deleted rather
than zero-filled. The domain tag is a fixed byte string independent of the
container version, so a container version bump does not change it. The signature
is raw Ed25519 over that message, verified with `verify_strict`, so a
non-canonical key or signature encoding is refused.

**Crates chosen here, with their cost measured and recorded.** The token
`ed25519-dalek` 3 over `curve25519-dalek` 5 for verification, `x509-cert` 0.3
over `der` 0.8 (`spki` 0.8, `const-oid` 0.10) for strict DER and the certificate
profile, and `sha2` 0.11 for the key id. All are pure Rust with no build script
and no C compiler in the path that reads untrusted bytes. The exact dependency
count before and after is recorded in the ticket's implementation note and in
the contract's dependency paragraph.

**Key id rule, fixed here.** The key id of a public key is the first 16 bytes of
its SHA-256, computed over the raw 32-byte Ed25519 public key, never over the
SPKI wrapper. A carried identifier is never trusted. Revocation entries name
keys by that id.

**Refusal classification, fixed here** because `startup-policy` consumes it:
`BundleError::is_trust_failure()` answers true for the outcomes that mean
"this file claims a signature we do not trust": a missing or malformed
signature, a signature that does not verify, an empty chain, an unknown root, a
revoked key, an expired or not-yet-valid certificate, and every chain profile
violation. Those stop daemon start-up. The container-format outcomes (bad
magic, unknown container version, a span that does not account for the whole
file, bytes before the header, a non-canonical DER encoding, trailing bytes in
the chain region, more than eight links, a malformed certificate, a non-zero
reserved field) degrade that one bundle instead, because there is no evidence of
tampering, only a file this build cannot read.

**Existing abstractions to use.** `CallError`'s shape for the new error enum;
`Loaded`'s doc-comment style for the unsafe-free parse path; the workspace
dependency table; the integration-test support module in
`crates/plugin-runtime/tests/support/` for building real artifacts on disk.

**Do not reimplement.** No hand-rolled DER or ASN.1 parser: `der` and
`x509-cert` own the decoding, and the strict decoder is what refuses
non-canonical input. No hand-rolled Ed25519, no `ring`, `openssl`, `aws-lc` or
any other crate that needs a C toolchain. Do not add `rustls-webpki`: its trust
anchor model and its name constraints are not this project's profile. No ZIP
reading in this ticket, since the verifier only has to cover the bytes. No
reading of daemon configuration. No change to the ABI types.

**Seams, for user approval.** One product seam: the public
`verify_bundle(bytes, &TrustStore)` entry, tested from
`crates/plugin-runtime/tests/bundle_verification.rs` with real bytes. One data
fixture: committed bundle vectors with altered copies under
`crates/plugin-runtime/tests/vectors/`. One test-only helper: a signer in
`tests/support/` that issues a small chain and signs a payload with a fixed
test seed, used to build the vectors and to install the test key as a root
explicitly. The daemon's compiled-in root set stays empty, so no shipped build
trusts the test key.

**Interface contract.** `VerifiedBundle::archive()` returns the ZIP bytes,
`VerifiedBundle::leaf_common_name()` returns the name the manifest check
compares against, `VerifiedBundle::header()` returns the parsed header, and
`BundleError::is_trust_failure()` classifies the outcome. `bundle-extraction`
consumes `archive()`, `manifest-and-library` consumes `leaf_common_name()`, and
`startup-policy` consumes the classification.

**Doc edits.** `docs/plugin-contract.md` gains a section for the container
header, the chain profile, the domain tag, the key id rule, the revocation rule
and the refusal rules, and the dependency paragraph records the measured count.
`docs/testing.md` gains the vector test if it runs as its own command.

## Level 1

### `bundle-extraction` (feature, m)

**Exports.** `plugin_runtime::bundle::extract`: a function that takes an
accepted `VerifiedBundle` plus this host's target and returns a `StagedBundle`,
or a `StageError`. `StagedBundle` owns a temporary directory and removes it when
dropped, so a failed load leaves nothing behind. It exposes the staged root, the
manifest's path and this host's library path.

**Targets.** A target is one string, operating system and architecture joined
by a hyphen, such as `linux-x86_64`, derived from `std::env::consts::OS` and
`ARCH`. A bundle's library path per target is `lib/<target>/<file name>`. The
archive root carries `manifest.toml` plus one directory per target.

**Rules the ticket enforces and records in the contract.** Refuse an absolute
entry name; refuse an entry name carrying `..`; refuse a symlink, hardlink or
directory entry; refuse an entry that declares a Unix mode other than the one
the host itself writes; refuse an archive above the entry count, the total
uncompressed size or the per-entry size limit. Every entry is validated, even
when its target is not this host's, and only the root manifest and this host's
target directory are written to disk.

**Existing abstractions to use.** The `zip` crate for the archive reader, with
default features off and only pure-Rust deflate on, so no C dependency enters
the path. `std::fs` with the host's own fixed modes, rather than applying the
archive's. `StagedBundle`'s `Drop` for the cleanup rule, matching the ordering
discipline the rest of the runtime uses.

**Do not reimplement.** Do not hand-roll the ZIP reader; do not enable
`zip`'s `bzip2`, `zstd` or `aes` features, all of which bring C or crypto
dependencies into the trusted path; do not re-verify the signature (already
done); do not parse the manifest here.

**Seams.** One product seam: `extract(verified, target)` -> `StagedBundle`,
tested from `crates/plugin-runtime/tests/bundle_extraction.rs` against both a
well-formed bundle and a hostile archive built inside the test. Cleanup is
asserted by the filesystem after the `Drop`.

**Interface contract.** `StagedBundle::root()`, `::manifest_path()`,
`::library_path()`, and a `Drop` that removes the staging directory. Both
`manifest-and-library` and `async-initialisation` consume it.

### `abi-initialisation-entry` (feature, l)

**Exports.** The amended plugin table in `plugin-contract`: the
`create_instance` slot becomes the asynchronous `init_plugin` slot, and the
counters slot does not exist anywhere in the table. `METIS_ABI_MINOR` is bumped
because the table changed; the entry symbol keeps major 1, so
`metis_plugin_entry_v1` is unchanged. The new entry receives one envelope
payload carrying the configuration and the host context, and returns two out
parameters: the instance and a future that must resolve successfully before the
instance is valid. The host-side driver for that future lands in
`async-initialisation`, not here.

Everything that describes the table moves in this one ticket and in one commit:
the contract text in `docs/plugin-contract.md`, the generated C header, the slot
constants and thresholds in `src/abi/layout.rs`, the static assertions in
`c/layout_static_asserts.c`, the Rust fixture, the C plugin and the ABI harness.

**Existing abstractions to use.** The size-prefixed, append-only table rule and
`MetisAbiError`'s version gate as they are. The `authoring` feature gate and
`plugin_adapter` for the Rust side of the new entry. `payload.rs` for the
configuration and host context envelope. The header regeneration script and the
`no_plugin_thread` and `feature_gate` tests as they are.

**Do not reimplement.** No second table type and no per-version entry wrapper.
No async runtime and no executor: the entry returns a table-defined future and
the host polls it. No serde types across the boundary, only the JSON envelope.
Do not keep the counters entry behind a flag for compatibility: the spec removes
it. Do not fix the MSVC static assertion form here; that is its own ticket and
it is blocked by this one.

**Seams.** Two. The ABI harness
(`cargo run -p plugin-fixture --bin abi-harness`), which hand-drives
initialisation with a configuration and host context payload, observes an
instance and a resolved future, and prints one line per check. The contract
tests (`crates/plugin-contract/tests/abi.rs`, `c_layout.rs`,
`no_plugin_thread.rs`) plus the C plugin build
(`bash scripts/build-c-plugin.sh`) and the header regeneration check.

**Interface contract.** The new slot's constant and name, the initialisation
payload's fields, and the two out-parameters. `manifest-and-library` resolves
the entry symbol and reads the amended table; `async-initialisation` calls the
entry and drives the returned future; the SDK effort consumes the same surface.

## Level 2

### `c-static-assert-msvc` (bug, s)

**Exports.** No product surface change. The contract's C translation unit
compiles under MSVC's C mode with warnings denied, so the Windows job widens
from `api-contracts` alone to the daemon, and the recorded gap in
`docs/testing.md` narrows or closes.

**Do not reimplement.** Do not drop the layout check or move it to a place MSVC
can silently skip. A deliberate mismatch must still fail the build under gcc and
clang, which is the test that proves the fix did not trade the check for
compilation.

**Seams.** The bug doc `docs/bugs/plugin-contract-c-static-assert-msvc.md` and
its recorded reproduction, the C plugin build under the pinned compilers, and
the CI workflow file.

### `manifest-and-library` (feature, m)

**Exports.** `plugin_runtime::manifest`: a `Manifest` type with
`Manifest::parse(text: &str) -> Result<Manifest, ManifestError>`, the plugin
identity and version, `abi_major`, `min_abi_minor`, per-target library paths,
the capability list with each capability's name, kind, version, request schema
and response schema, and the configuration schema. Plus target selection, which
returns this host's library path from a `StagedBundle`, and the mapping step
that turns a validated manifest plus a selected library into a `Loaded` with a
table the existing raw ABI checks accept.

The refusals are distinguishable: absent manifest, invalid manifest naming what
is wrong, no library for this target, a missing entry symbol, a major mismatch,
an older minor refused before any entry is read, and a table too short for an
entry this build needs.

**Existing abstractions to use.** `toml` for the text format, added to the
workspace dependency table. `plugin_contract::capability::CapabilityDescriptor`
for the capability list, so the manifest's list and the library's report are the
same type. `Loaded` and `MetisAbiError` for the mapping and the version gate,
unchanged. `ManifestError` follows the existing error style.

**Do not reimplement.** No second capability descriptor type. No schema
inference in the manifest: the schemas are declared text, and the library's
`list_capabilities` is the cross-check, which is `async-initialisation`'s step.
No new ABI rules: the version checks stay the landed ones. Do not cross-check
the capability list here; the cross-check needs a live instance and belongs to
the load entry.

**Seams.** One product seam: `Manifest::parse` plus `Loaded::open(lib_path,
&Manifest)` driven from `crates/plugin-runtime/tests/manifest.rs` against a
staged bundle whose manifest is hand-written, so the format is provably not
generator-only. The existing raw ABI checks and the ABI harness must still pass
on a library mapped from a bundle.

**Interface contract.** The validated `Manifest` value and `ManifestError`'s
variants, consumed by `async-initialisation` (cross-check and registration),
`startup-policy` (the disable reasons) and `sample-bundle-ci` (the hand-written
manifest). The contract gains the manifest's field names and types as the format
an author writes by hand.

## Level 3

### `async-initialisation` (feature, l)

**Exports.** One asynchronous load entry on `plugin-runtime`:
`load_bundle(bundle_path, config, host_context, &TrustStore) -> impl
Future<Output = Result<Serving, LoadError>>`, composing verification,
extraction, manifest validation, library selection, the ABI check, the
initialisation call, the capability cross-check and registration. `Serving`
carries the registered instance name, the `Arc<Instance>`, and the descriptor
list it registered.

The configuration and the host context are the runtime's own value types, built
by the daemon and delivered in one payload. The plugin's setup failure falls
into two classes the caller can tell apart: the plugin is defective, or the
configuration does not match what the plugin declared. The capability
cross-check refuses with the name of the capability that differed.

**Existing abstractions to use.** `Registry::register`, `Instance`, `Host` and
the payload envelope as they are. `LoadError` composes `BundleError`,
`StageError` and `ManifestError` rather than restating them, and folds into the
existing partition of load and dispatch, routing and registration.

**Do not reimplement.** No runtime and no thread, still. No second registration
path. No schema validation changes: `Registry::validate_request` and
`validate_response` stay the seams. No deadline or cancellation policy in this
ticket; that is level 4.

**Seams.** One product seam: `load_bundle` driven from
`crates/plugin-runtime/tests/load.rs` against a real bundle built in the test
from the fixture cdylib with a hand-written manifest, dispatching one capability
through the registry and checking the response. The ABI harness and the
contract tests stay as they are.

**Interface contract.** `load_bundle` and `Serving`, consumed by
`startup-policy`, `call-cancellation`, `callback-sink`, `teardown-and-release`
and `sample-bundle-ci`. The future is caller-driven, so the caller's runtime
decides when plugin code runs.

## Level 4

### `call-cancellation` (feature, m)

**Exports.** `Instance::cancel_all(deadline) -> CancelReport`, the drop rule on
`PluginCall` (release every buffer the host still holds for the call and cancel
its outstanding service requests), and the ledger entries for an
unacknowledged cancel. Cancelling an unknown or finished id answers the frozen
not-found status without calling the plugin; a second cancel of a live id is
accepted; a completion offered for a released context is refused rather than
delivered. An unacknowledged cancel does not quarantine.

**Existing abstractions to use.** `Instance::cancel` and the in-flight set,
`Instance::complete_service`, the ordering ledger, the frozen
`MetisStatus` space, and the fixture's cancellation token. No timer and no
default deadline: the runtime holds neither.

**Do not reimplement.** No timer, no runtime, no new status variant for
cancellation. Do not add a quarantine path for a slow call: quarantine stays
reserved for an abandoned poll and an unreleasable teardown.

**Seams.** One product seam: the public instance and call API, tested from
`crates/plugin-runtime/tests/cancellation.rs` with a cancellable fixture
capability, including the dropped-before-acknowledgement case and the
post-drop completion refusal. The ledger's contents are the assertion.

### `callback-sink` (feature, m)

**Exports.** `plugin_runtime::sink`: one `Sink` trait with a method per callback
kind (progress, event, log, service request), set at `Host` construction with
`Host::with_sink`, plus a recording default that keeps the existing accessors
and tests working. Every callback names the instance; progress and service
requests also carry the request id; an event carries its topic and payload and
no request id, because the frozen ABI callback has none; a log carries a typed
level. Payloads arrive as owned copies taken before the plugin's buffer is
released. Sink methods cannot fail and must not block, a panic inside one is
caught in its own frame and recorded, and delivery is ordered per instance. A
service request's return value is the status the ABI expects, with the answer
delivered later through the existing completion entry. The host-facing frames
are asserted panic-free in a dedicated CI step.

**Existing abstractions to use.** `Host`'s existing recorded callbacks and
accessors (`logs`, `events`, `pending_services`, `ordering`) become the default
sink's storage, so the existing tests and the ABI harness do not change.
`catch_unwind` with `AssertUnwindSafe`, as the rest of the crate already does.
`flagset` or a plain enum for the log level in the Rust API, with the integer
mapping at the ABI edge.

**Do not reimplement.** No queue and no backpressure in the runtime: a daemon
that wants either puts it behind the sink. No second callback path for logs.
Do not let the sink call back into the runtime or the plugin.

**Seams.** One product seam: `Host::with_sink` plus the four callbacks, tested
from `crates/plugin-runtime/tests/sink.rs`. One build-level check: the
`no_panic` assertion over the host-facing frames, added to `docs/testing.md` as
a command that runs only in a dedicated CI step with the feature enabled, and
documented there as the only place the assertion holds.

### `startup-policy` (feature, m)

**Exports.** `plugin_runtime::startup`: `start_plugins(dir, config, trust) ->
StartupReport` over a directory of bundles, applying the documented outcomes.
A trust failure, an absent or invalid manifest and a refused unload stop
start-up. An extraction refusal, a missing target library, an ABI mismatch, a
manifest that disagrees with the library, and an unknown container version
disable that one plugin and leave the daemon running. `StartupReport` lists the
serving instances and the disabled placeholders, each with its name and reason,
and a placeholder is built from the manifest when one was readable, otherwise
from the bundle's file name with no capabilities. Placeholders are listable, are
excluded from the capabilities an agent would be offered, and answer the
existing disabled route error carrying the reason.

**Existing abstractions to use.** `BundleError::is_trust_failure` for the
stop-versus-disable split, `LoadError` for the per-plugin outcomes, and
`Registry`'s existing entry and route-error surfaces for the placeholder's
behaviour. The policy itself is a table in the crate, documented in
`docs/plugin-contract.md`.

**Do not reimplement.** No second registry and no second route error. Do not
turn a trust failure into a placeholder, and do not turn an unreadable file into
a stop. Do not scan the filesystem recursively or invent a discovery format
beyond the plugin directory.

**Seams.** One product seam: `start_plugins(dir, config, trust)` tested from
`crates/plugin-runtime/tests/startup.rs` over a temporary directory holding a
mixture of good bundles, one per refusal kind, including the unknown container
version case, which is the only refusal that degrades without its manifest ever
being read.

## Level 5

### `teardown-and-release` (feature, m)

**Exports.** `Serving::release(deadline) -> ReleaseReport`: unregister the
instance, cancel or drain in-flight calls to the caller's deadline, call the
plugin's shutdown entry, drop every future, destroy the instance, unload the
library, and report the ledger entries added. An instance that cannot be
released stays mapped and is reported, which covers a shutdown that returns a
non-ok status, a quarantined instance whose abandoned poll never returns, and an
unload refused for any reason. Disabling and enabling are registry state only:
they refuse or accept new calls and touch neither in-flight calls nor the
library. The daemon's shutdown deadline ends the wait and produces the report.

**Existing abstractions to use.** `Instance::unload`, `Instance::shutdown`,
the ordering ledger, `instance.is_quarantined()`, and `Registry::enable`. The
unload guards stay: the in-flight set, the last `Arc`, and the rule that the
table is dead after `destroy_instance`, as the hazard findings settled. No
outstanding-clone gate is added.

**Do not reimplement.** No clone counter and no outstanding-clone gate. No
forced unmap of a library that might still run. No live teardown or
reconfiguration: unload happens at shutdown.

**Seams.** One product seam: `Serving::release(deadline)` with the ledger as
the assertion, tested from `crates/plugin-runtime/tests/teardown.rs`. One
subprocess fault test for a drop after unload, because the behaviour under test
is a fault; it runs as a child process and asserts the signal, matching the
hazard prototype's method.

## Level 6

### `sample-bundle-ci` (feature, m)

**Exports.** The end-to-end gate, not new runtime surface. A packaging step
(`scripts/pack-sample-bundle.sh` or an equivalent test-support builder) writes a
signed bundle holding the C fixture's library and a hand-written manifest,
signed with the test key, and a CI step runs an integration test that loads that
bundle through the public load entry, dispatches a capability, observes at
least one event through the sink, and releases the instance with the ledger
asserting the teardown order. The same test fails when one byte of the bundle is
altered or when the chain is signed by a key that is not a configured root.
`docs/testing.md` and `.github/workflows/ci.yml` gain the step, and the
daemon's compiled-in root set stays empty.

**Existing abstractions to use.** The test signer, the vectors and the
packaging helper the earlier tickets built, the C fixture and its hand-written
manifest, the ABI harness's one-line-per-check style, and the runtime's support
module that rebuilds the fixture before loading it, so a stale library cannot be
tested.

**Do not reimplement.** No second packaging format, no second loader, no SDK.
The manifest is hand-written and stays hand-written: the C fixture is the proof
that the format is writable without a generator.

**Seams.** The single end-to-end seam, which is the public load entry plus the
sink plus the release entry. The CI step is the gate.

## Testing seams, collected

- `verify_bundle(bytes, &TrustStore)` in `bundle-verification`, with committed
  byte vectors and a test signer.
- `extract(verified, target) -> StagedBundle` in `bundle-extraction`.
- `Manifest::parse` plus `Loaded::open` in `manifest-and-library`.
- `load_bundle(...) -> Serving` in `async-initialisation`.
- The instance and call API, plus the ledger, in `call-cancellation`.
- `Host::with_sink` and the four callbacks in `callback-sink`, plus the
  panic-free build check in its own CI step.
- `start_plugins(...) -> StartupReport` in `startup-policy`.
- `Serving::release(deadline)` in `teardown-and-release`, plus the subprocess
  fault test.
- The end-to-end bundle gate in `sample-bundle-ci`.
- The ABI harness, the contract tests, the C plugin build and the header
  regeneration check continue to gate every change.

## Dependency posture

- `plugin-runtime` gains the signature, certificate and archive readers:
  `ed25519-dalek` 3, `x509-cert` 0.3, `der` 0.8 and `sha2` 0.11 for the trusted
  parse path, and `zip` with pure-Rust deflate only for extraction. All of them
  are pure Rust, none has a build script that compiles C, and none is
  feature-enabled beyond what the ticket needs.
- `plugin-contract` gains nothing. Its `authoring` feature stays off for
  `plugin-runtime`, so the host sees the primitives and the envelope alone.
- The daemon's own dependencies are out of scope here.
- The measured dependency count for `plugin-runtime` is recorded by
  `bundle-verification`, and no later ticket adds a dependency without the same
  measurement.

## Out of scope for this effort

Restated so no chain reaches past its ticket: the plugin authoring SDK, the core
plugin set and the signing CLI (`metis-plugin-sdk`), the daemon's discovery and
configuration resolution and its realtime forwarding, hot unloading, sandboxing
or any claim that the ABI is safe, workflow step implementations and the agent
loop, and multi-target bundles beyond selecting the one library that matches
this host.
