## What to build

The credential lifecycle: a surface pairs once with a preshared key, receives its
own token, stores it safely, and can be revoked on its own without disturbing
other surfaces.

## Acceptance criteria

- [ ] The pairing call is gated by a preshared key resolved from configuration as
      a literal, an environment reference, a keystore reference, or a secret-file
      reference, and a secret file readable by group or others is refused with a
      clear error.
- [ ] A successful pairing mints an opaque per-surface token, the daemon stores
      only its hash, and the token is returned once.
- [ ] The credential travels as authorization metadata on every call including
      the event stream, and never appears in a URL.
- [ ] Missing credentials and invalid or revoked credentials produce
      distinguishable typed errors, and the client maps them so a caller can tell
      pairing is needed from access being gone.
- [ ] Removing one token entry and restarting revokes that surface while the
      other surfaces keep working, asserted by a test.
- [ ] The client keeps the credential in the platform keychain when its command
      line tool is available, falls back to an owner-only file, and reports the
      fallback.
- [ ] A paired client reaches the full exposed surface, with no per-client
      permission filtering.

## Blocked by

- `local-identity-and-acl`, because pairing is an authenticated call on the local
  transport and needs the identity handshake.
- `state-store`, because the daemon keeps token hashes in the SQLite store that
  ticket lands, and this ticket adds no file format of its own. The preshared key
  travels in the pairing request body, and the token is kept by the client, never
  in the store.

## Implementation notes

Landed on `task/pairing-and-tokens` as the merge commit `1c89660`
("ticket(pairing-and-tokens): Pairing, per-surface tokens, and client credential
storage"), parents `97e0a91` and `7dc60b1`. `97e0a91` is the landing branch,
created at `main`'s tip, which already carries the `state-store` landing merge
and the `serve-tcp-service` follow-up docs commit; `7dc60b1` is the working
branch `ticket/pairing-and-tokens`, nine `wip:` commits. The merge was clean with
no conflicts. The landing tree differs from `7dc60b1` only by the three docs
files that `97e0a91` added (`docs/tasks/metis-foundations/map.md`, the
`remote-pairing` ticket and the new `serve-tcp-service` ticket), so every source
file landed byte for byte as verified. `ticket/pairing-and-tokens` was deleted
after the merge, and the deviation report is committed at
`docs/tasks/metis-foundations/tickets/pairing-and-tokens/deviation-reports/pairing-and-tokens.md`.

Gates, run on the landing tree through `devenv shell --`: `cargo fmt --check`
exit 0; `cargo clippy --all-targets -- -D warnings` exit 0, the only output being
the pre-existing `plugin-contract` `cc` build-script `_FORTIFY_SOURCE` note,
which is not a clippy diagnostic; and the workspace `cargo test` exit 0 with 140
passed, 0 failed and 7 ignored. The 7 ignored are pre-existing doc-tests inside
the generated connect tree and `plugin-contract`; no test under `crates/`
carries `#[ignore]`.

What landed: the contract appends `Pair` and its messages to
`contracts/proto/metis/v1/daemon.proto`, with the generated trees regenerated by
the committed script. `crates/api-contracts/src/auth.rs` holds the credential
wire vocabulary (the authorization header name and the bearer spelling) that
both ends must spell identically, and `src/time.rs` moves `rfc3339` and
`rfc3339_now` out of the client so the daemon service can stamp its own replies.
`daemon/src/secret.rs` resolves one string into the preshared key with the
prefixes `literal:`, `env:`, `keystore:` and `file:`, plus a bare value read as a
literal, through `SecretRef::PRESHARED_KEY_ENV` (`METIS_PRESHARED_KEY`) and
`resolve_preshared_key()`, and refuses a secret file readable by group or others
with `SecretError::TooPermissive { path, mode }` naming both. `daemon/src/auth.rs`
holds `AuthPolicy`, `AuthError`, `RejectionCause`, the `Granted` identity, the
`AuthInterceptor` whose unary and streaming halves share one private `admit`, and
`pair(store, preshared, surface, presented)`, which mints the opaque token,
stores only its SHA-256 hash under the rule `state-store` pinned, and returns the
text once. `daemon/src/service.rs` builds the authorized service.
`client/src/credential.rs` keeps the credential in the platform keychain when
its tool is on `PATH` and otherwise in an owner-only file (600, inside a 700
directory), reporting which backend it used; `client/src/lib.rs` attaches
`Authorization: Bearer` as a default header on every call, never in a URL, and
maps missing, invalid and revoked credentials to separate typed errors,
`CredentialMissing` and `CredentialRejected { cause }` with `Invalid` or
`Revoked`. `docs/dev-env.md` and `docs/testing.md` carry the new variable, the
modes and the run commands.

Every acceptance criterion maps to a passing test on the landing tree:
`daemon/tests/secret.rs` (12), `daemon/tests/auth.rs` (10), `daemon/tests/token.rs`
(4), `client/tests/credential.rs` (5), `api-contracts/tests/keychain.rs` (5) and
`api-contracts/tests/contract.rs` (4), plus unit tests inside
`daemon/src/auth.rs` and `api-contracts/src/time.rs`. The authorization suite was
shown to be load-bearing by a mutation check: pinning
`AuthInterceptor::needs_credential` to `false` fails exactly the four refusal and
revocation tests.

Divergences, all inside the recorded approval and detailed in the deviation
report: `daemon::service::service(...)` returns `ConnectRpcService<Router>`
rather than the spec's `router(...) -> Router`, because connectrpc 0.9.1 keeps
the interceptor chain on `ConnectRpcService` and offers no conversion back, so
`api_contracts::transport` gained `serve_uds_service` to mount it;
`Client::with_surface` is now fallible and `Client::pair` takes `&mut self`, which
the landed `crates/client/tests/identity.rs` absorbed with two `?`s and no
assertion change; and the additive public surface named above is unplanned but
required by the criteria.

Residual risks carried into the daemon effort:

- The streaming half of the interceptor has no wire test, because the contract
  declares no streaming RPC yet. It is proven by construction through the shared
  `admit`, and `event-stream` exercises it.
- The landed TCP front-ends take a bare `Router`, so an authorized service cannot
  be mounted on TCP yet. That gap is outside this ticket's criteria and is owned
  by `serve-tcp-service` on `main`, which `remote-pairing` is blocked by.
- A store fault during verification fails closed as
  `CredentialRejected { Invalid }`, because `AuthError` carries the two spec'd
  causes; the enum is non-exhaustive, so a store-fault variant stays additive.
- The secret file access rule is Unix-only, and keychain absence versus refusal
  is inferred from the tool's exit status and standard error, so a silently
  failing tool reads as absence. macOS compiles but is never run against the real
  `security` tool.
- A wrong preshared key reaches the client as `ClientError::Call` carrying
  `PermissionDenied` rather than as a typed pairing error; the spec names none,
  and the typed credential mapping covers the credential path only.

Knowledge harvested at finalize: the effort map gained the decision bullet for
the credential lifecycle and for the fact that a listener mounts a
`ConnectRpcService` rather than a `Router`. `docs/dev-env.md` and
`docs/testing.md` already carried the secret reference forms, the access rule,
the token file, the keychain rule, which transport needs a credential and the run
commands, so they needed no further change. Chain history worth knowing: the
first run of this ticket was green in tdd and verify but its deviation step wrote
the report to the workflow artifact instead of the ticket's `deviation-reports`
path, so the chain's file gate failed; the retry re-verified the unchanged tree,
let the reporter write the file, and landed.
